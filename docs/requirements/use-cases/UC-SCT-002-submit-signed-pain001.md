# Submit a signed pain.001 instruction
**Business process:** BP-01; **scope/level:** system; **primary actor:** payment submitter; **supporting:** signature, ingress, ISO-adapter. **Interests:** source evidence precedes mapping. **Trigger:** a signed pain.001 arrives.
## Preconditions and guarantees
Tenant/profile and verification material are available. Minimal: raw source and verdict evidence survive failure where permitted. Success: verified source is mapped as one instruction and proceeds through UC-SCT-001.
## Main success scenario
1. Submitter supplies signed pain.001. 2. Debina identifies channel/tenant. 3. Debina preserves source evidence and verifies signature. 4. Debina validates/maps the applicable message. 5. Debina delegates accepted instruction handling to UC-SCT-001. 6. Debina returns correlation and outcome. When the submitter uses the Debina web interface, they select the signed pain.001 artifact, submit it once, receive a deterministic accepted or created outcome, and can open the resulting payment detail view.
## Extensions and failure flows
3a. Signature fails: record verdict/evidence and reject with a stable outcome; no mapping or payment. 4a. Version/structure is unsupported: reject with preserved source correlation. 4b. E1 profile validation fails (transaction count, payment method, control sum): reject without persisting validated-only fields as domain data. 4c. Debtor or creditor IBAN fails mod-97 check-digit validation: reject at mapping with a stable field-path outcome; no payment row. 4d. Instructed amount currency is not EUR under the current educational SCT profile: reject at mapping; no payment row. `[PROJECT_SIMULATION]` — scheme certification and non-EUR rails remain `BLOCKED_FOR_PRODUCTION`. 4e. Optional UETR is present but not RFC 4122 UUID version 4: reject at mapping; no payment row. 5a. Replay with the same tenant, idempotency key and payload returns the original outcome; same key with a different payload returns conflict.

## Special requirements and variations
QS-SEC-02, QS-TRC-01, QS-INT-01. Privacy: raw evidence access is source-owned. Data/commands: signature verification, ingress evidence, mapping; transaction boundary source-evidence-and-payment. Variations: unsigned JSON_DIRECT is out. No volume target. Timestamp semantics (project interpretation): when a verified pain.001 is mapped, Debina preserves `GrpHdr/CreDtTm` as the **source message creation timestamp** when present. Debina **receive** and **record/processing** times are separate system timestamps and must not replace or silently reinterpret source creation time. Historical rows without a recoverable source `CreDtTm` keep source creation time **unknown**. Evidence and operational reads must keep these timestamps distinct (source creation must not drive receive/SLA ordering). CreDtTm parsing (Debina project interpretation, not EPC/ISO normative): when `CreDtTm` carries an explicit offset it is converted preserving the instant; when it is offset-less the current educational profile interprets it as UTC.
